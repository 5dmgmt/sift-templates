## Step 1: まず自分で書く

3. 自社業務で「毎回同じ手順で依頼している」ものはある？
4. AIとの協働で「仕組み化したい」業務 (件数は問わない / 複数可 / 該当なしも本人の今の実感として扱う)

※ ここで書いた「仕組み」の定義は、この後のワークで正式に言語化します。

**対話を深めるための補助情報 (シコファンシー = 過度な同意)**:
AIは、会話の流れによって同意寄りの応答を返すことがあります。
重要な判断では、反対意見、Claude のサブエージェントの意見、一次資料も参考にし、最終判断はご自身で行ってください。
多くの応答は本来の共感・支持で問題ありません。ただし「ここは大事な決断だ」「もう一段
別の角度から見たい」と感じた時に、以下の選択肢を持っておくと役立ちます:
- 反対の立場から論拠を出してもらう (「逆の意見だとしたら何？」)
- 第二意見は、Claude にサブエージェントで取ってもらいます
- 「私の判断で見落としている前提を 3 つ挙げて」と頼む
Claude を疑い続ける必要はありません。Claude との信頼ある対話を保ちつつ、
検証ツールを「必要な時に使える」状態にしておく、それだけで十分です。

### Step 1: 3 つの層を定義（1 ターン 1 層）
Claude が 60101 / 60102 の実験を引用しながら、1 ターンに 1 層ずつ以下を提示し、受講者に「修正したい点はあるか」を 1 問だけ聞く:
- **プロンプト層**: 1 回の依頼で「何をしてほしいか」を伝える指示 (1 文 + 役割)
- **文脈層**: AI が判断の土台にする背景情報 (1 文 + 役割)
- **仕組み層**: プロンプト + 文脈 + レビュー手順 + 更新ルールを束ねた再利用可能な業務設計 (1 文 + 役割)

カタカナ用語を避け、経営者が直感的に分かる言葉で書く。

### Step 2: 3 層が「なぜ必要か」を整理
Claude が以下 3 点を 60101-60102 の実験結果を引用しながら整理して提示する:
- プロンプトだけでは不十分な理由 (60101 引用 = Phase ID + セクション名 + 要約のみ、生プロンプト / 生 AI 出力転記禁止)
- 文脈を加えると何が変わるか (60102 引用 = 同上)
- 仕組みにすると何が変わるか (推論 + 仮説)

### Step 3: 自社業務 (件数は問わない) で 3 層の骨格 + 安全領域分離
Claude が事前メモで挙げた業務について、以下を提示する:

**通常 3 層骨格から外す停止条件 (= 別欄送り)**:
- 本番 Supabase 操作 / RLS 緩和 / service_role 使用 / migration 実行 / DB 構造変更
- 課金 / 決済 / 価格変更 / 解約処理
- 顧客通知 / 顧客 DM / メール送信 / SMS / プッシュ通知
- 契約書 / 法務判断 / 医療判断 / 税務判断 / 労務判断
- 違法行為 / DV / 自殺念慮等の危機兆候保護領域
- 該当する業務を選んだ場合、AI は draft / sandbox / test data のみ扱い、人間最終責任者の承認 + 必要時の専門家確認を必須化し、「専門家確認 / 安全確保優先」欄に分離

**通常 3 層骨格 (上記に該当しない業務)**:
- **対象業務**: 業務名 (抽象化) / 頻度 / 現在の進め方 (placeholder で記録)
- **プロンプト層**: この業務で使うプロンプトの骨格 (行数は問わない、固有名 placeholder)
- **文脈層**: この業務に必要な文脈ファイル候補のリスト (件数は問わない / 複数可) (`~/sift/` 配下の成果物に限定、各ファイル名 + 該当 Phase ID + 1〜2 行要約 + redaction 状態欄 = `redacted_ok` / `needs_redact` / `未確認 (60201で確認)` / `raw_only` / `expert_review` のいずれかを記録。本 Phase の Read allowlist は作業ファイル + 60101 + 60102 の 3 件のみのため、候補ファイル本体の redaction 検証は 60201 に持ち越し)
- **仕組み層**: レビュー手順 / 更新ルール / 成果物テンプレートの概要

最後に「Part 602 で整理すべき文脈ファイル」「この骨格を完成させるために不足している情報」を提示し、受講者に修正案を 1 問だけ聞く。
